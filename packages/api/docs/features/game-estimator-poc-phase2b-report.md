# Phase 2-B: 历史对局日志分析与逐轮披露验证

## What

对本地 211 局历史对局数据（`bidking-history.sqlite`，739MB，13,768 条事件）进行了完整分析，验证了逐轮披露机制的实际格式和样本池匹配的可行性。

### 数据概况

| 指标 | 数值 |
|------|------|
| 总局数 | 211 |
| 日志事件总数 | 13,768 |
| 协议消息类型 | 37 种 |
| GameStartNotify | 211 条 |
| GameNextRoundNotify | 489 条 |
| GameOverNotify | 212 条 |
| GameUseItem | 798 条 |
| GameBid (含 C2S/S2C) | 2,076 条 |

### 关键发现 #1：两层渐进披露模型

HitBoxList 中的条目有两类，按 `ItemCid` 区分：

```
隐藏箱子（Cid:0）:  {BoxId:44, ItemCid:0, ItemQuility:0, ItemType:[], ItemSlotType:11}
揭示物品（Cid>0):  {BoxId:50, ItemCid:1103005, ItemPrice:8880, ItemQuility:3, ItemType:[110,101], ItemSlotType:54}
```

**第一层**：位置披露（BoxId 可见，内容不可见）  
**第二层**：物品披露（品质、价格、品类、Cid 全部可见）

| 轮次 | 事件数 | 位置披露 avg | 物品披露 avg | 物品均价 |
|------|--------|-------------|-------------|---------|
| R1 | 178 | 1.3 | 0.8 | 12,148 |
| R2 | 155 | 1.3 | 0.6 | 13,529 |
| R3 | 108 | 1.4 | 0.6 | 14,540 |
| R4 | 48 | 0.9 | 0.6 | 15,219 |

趋势：均价逐轮上升（R1 12k → R4 15k），说明高品质物品倾向于后轮披露。

### 关键发现 #2：GameStartNotify 时 StockContainer 为 null

R0（游戏开始时的 GameStartNotify）中，StockContainer 字段为 `null`。物品全部通过 MapSkillLog.HitBoxList 逐轮披露。这意味着：
- **初始可观测信息**：仅 MapSkillLog.HitBoxList 中的 R0 条目（平均 2.0 个物品，58% 对局为 0）
- **品质分布只能在 GameOver 后确认**

### 关键发现 #3：物品形状分布（真实数据 vs 模拟器）

从 30 局 GameOverNotify 的 BoxPositionData 提取（1,105 件物品）：

| 面积 | 占比 | 对应形状 |
|------|------|---------|
| 1 | 41.8% | 1x1 |
| 2 | 18.6% | 1x2 / 2x1 |
| 3 | 1.3% | L-shape(3) |
| 4 | 28.0% | 2x2 |
| 6 | 5.4% | 2x3 / 3x2 |
| 9 | 2.4% | 3x3 |
| 其他 | 2.5% | 5,8,10,12,15,16,20 |

**需要调整**：模拟器的 shape tier 分配过于均匀。真实数据中面积 1 和面积 4 合计占 70%，面积 2 约占 19%。按品质分层的平均面积：

| 品质 | 平均面积(cells) | 物品数 |
|------|---------------|--------|
| Q1 白 | 1.7 | 909 |
| Q2 绿 | 2.1 | 1,489 |
| Q3 蓝 | 2.8 | 1,920 |
| Q4 紫 | 2.9 | 1,852 |
| Q5 橙 | 3.6 | 529 |
| Q6 红 | 3.9 | 210 |

### 关键发现 #4：最终品质分布（211 局汇总）

| 品质 | 数量 | 占比 |
|------|------|------|
| Q1 白 | 909 | 13.2% |
| Q2 绿 | 1,489 | 21.6% |
| Q3 蓝 | 1,920 | 27.8% |
| Q4 紫 | 1,852 | 26.8% |
| Q5 橙 | 529 | 7.7% |
| Q6 红 | 210 | 3.0% |

**总计**：212 局，6,909 件物品，平均 32.6 件/局，平均 188.2 个总格子/局。

填充率仅约 17.5%（33/188），远低于模拟器现有的 75% WAREHOUSE_FILL_RATIO。

### 关键发现 #5：轮次分布

| 轮数 | 对局数 | 占比 |
|------|--------|------|
| 1 轮 | 23 | 12.9% |
| 2 轮 | 47 | 26.4% |
| 3 轮 | 60 | 33.7% |
| 4 轮 | 48 | 27.0% |

平均 2.7 轮。约 60% 的对局在 3 轮内结束。

### 关键发现 #6：Grid 布局可以从 BoxPositionData 还原

GameOverNotify 的 StockBoxes 中，每件物品的 `Item.BoxPositionData` 是相对于左上角的坐标数组。结合 `BoxId` 和 `Position{X,Y}` 可以还原完整的 10 列仓库布局。

示例（3x3 物品）：
```json
{"BoxPositionData": [{"X":0,"Y":8},{"X":1,"Y":8},{"X":2,"Y":8},
                     {"X":0,"Y":9},{"X":1,"Y":9},{"X":2,"Y":9},
                     {"X":0,"Y":10},{"X":1,"Y":10},{"X":2,"Y":10}],
 "Quality": 3, "Cid": 1053001}
```

这允许我们提取真实的 Polyomino 形状作验证集。

### 对匹配函数的影响

1. **L1 硬约束校准**：真实 totalCells≈188（非模拟器的估算值），itemCount≈33
2. **L2 软约束校准**：真实品质分布为 Q1:13% Q2:22% Q3:28% Q4:27% Q5:8% Q6:3%
3. **新增 L3 逐轮匹配**：不仅匹配最终状态，还要匹配每轮的 position-reveals 和 item-reveals 数量
4. **填充率修正**：从 75% 下调到 ~20%，模拟器生成的样本将更稀疏

## Why

### 为什么这个分析对匹配函数至关重要

1. **两层披露模型是之前未知的**：Phase 1 假设物品是逐轮"直接披露"的，但实际上位置披露（占 2/3）只告诉你"这里有个箱子"，不告诉你里面是什么。匹配函数需要区分这两类信息。

2. **真实品质分布与 Drop Table 权重分布不同**：Drop Table 的 weight 是"理论出现概率"，实际 211 局的频率分布偏向了中品质（Q3/Q4 各占 27%）。模拟器需要用真实分布校准采样权重。

3. **形状分布验证了架构决策**：面积与品质正相关（Q1=1.7 → Q6=3.9cells），但真实分布更集中（面积 1+4 占 70%）。模拟器的 shape tier 分配需要调整权重。

4. **填充率差异巨大**：模拟器用 75% 填充率，实际只有 17.5%。这意味着样本池中绝大多数样本的密度远高于真实对局，ε 阈值需要重新计算。

### 为什么不需要自己抓包

211 局历史数据已经足够做匹配函数验证。bidking-history.sqlite 的 protobufJson 字段直接可读，不需要运行 protobuf collector。数据采集链路已存在且可用。

## Tradeoff

| 决策 | 利 | 弊 |
|------|-----|-----|
| **用历史数据校准（非实时采集）** | 211 局足够统计显著；无需运行游戏 | 样本是历史版本，协议可能有变 |
| **匹配函数增加逐轮维度** | 匹配精度更高；可以利用时间序列信息 | 复杂度增加；需要每组样本存储逐轮状态 |
| **填充率从 75%→20%** | 样本更接近真实分布 | 模拟器需要调整算法（当前贪心拼图假设密集填充） |
| **形状 tier 从均匀→加权** | 样本形状分布更真实 | 失去了一些多样性 |

**推荐**：Phase 2-C 先做三件事：
1. 重新生成样本池（1M 样本，修正填充率+形状分布）
2. 写匹配函数原型（L1+L2，先用 211 局验证 ε 阈值）
3. 逐轮匹配留到 Phase 2-D

## Open Questions

1. **SlotType 编码含义**：HitBoxList 中 ItemSlotType=11/12/13/21/22/23/31/32/33/41/52/54 等，可能与容器类型或技能类型相关。逆向分析需深入 BidKing 代码。

2. **物品价格信息来源**：StockBoxes.Item 没有 ItemPrice 字段，价格仅在 HitBoxList 中。匹配函数是否需要价格维度？

3. **逐轮数据一致性**：同一局游戏中，HitBoxList 披露的物品是否与 GameOver 的 StockBoxes 一致？需做交叉验证。

4. **游戏版本演进**：211 局数据跨度多长？期间 Drop Table 是否有更新？如果权重有变化，需要分版本做样本池。
